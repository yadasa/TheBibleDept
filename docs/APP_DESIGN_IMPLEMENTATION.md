# App design and annotation implementation

## Experience

The active Expo client now opens in dark mode. Signed-in readers can select Dark or Light under Account → Settings; preferences are saved per account on that device. Guests use dark mode and cannot access Settings. Every screen, dialog, field, reader control, icon and status bar uses reactive semantic theme colors. Reading text size remains an independent preference.

The background repeats a cached rasterization of the original deterministic 1,000-fleck grain. Its 120-point tile, ink colors and 0.16 opacity are preserved at 1×, 2× and 3× density. Each of the five pages owns one orange circle in a separate measured SVG viewport, with a local gradient definition, center at 85% of page width and near the upper third, and radius capped at 210 points. The background travels with the page track and extends beneath the header, navigation and safe areas; the duplicate header grain layer is removed. The header and signed-out account screen use the actual textured TBD artwork from the public website's navbar, bundled locally as AVIF. [Asset provenance](../bibledept-mobile/assets/README.md) identifies the original source and grain pixel checks. The logo's alpha transparency and 580:229 aspect ratio are preserved, with no added backing or side padding. The header respects the safe area and adds 16 px of vertical clearance; the logo no longer overrides vertical centering.

Home shows **Today’s reading**, the date, a current-reading card with device plan progress, account streak and seven-day history, notes/prayer shortcuts, and the latest private note. It does not invent completed days, quotes, or activity to fill empty states. Plan continuation stays local; the chapter completion action writes the cloud reading day.

## Navigation source and motion

The user requested the navigation from `yadasa/church`. The reference was the local main checkout at commit [`e7b01d364f19965342d8ee69beb964e6a6a62a29`](https://github.com/yadasa/church/commit/e7b01d364f19965342d8ee69beb964e6a6a62a29), specifically [`LiquidBottomNav.tsx`](https://github.com/yadasa/church/blob/e7b01d364f19965342d8ee69beb964e6a6a62a29/apps/web/src/site/components/LiquidBottomNav.tsx) and its CSS. No Church repository files were changed.

The app ports five evenly spaced destinations and the selected indicator's motion to React Native Animated. The navigation has the restored frosted Church shell and an orange selected pill. Ordering is **Notes · Prayer · Home · Bible · Account**. Adjacent transitions retain the reference's 430 ms duration; each extra page crossed adds 90 ms, up to 700 ms. The indicator keeps `.22,.82,.18,1` easing, offsets `0/.24/.72/1`, stretch `min(abs(delta) × .42 + 14, 76)`, and trailing compression `min(stretch × .48, 34)`. It is recolored with Bible Dept semantic colors. Width changes settle safely; a newer destination interrupts the previous transition without committing its obsolete route.

The page position, background, and navigation indicator share one animation clock. All pages lie on a single horizontal track in nav order, so Notes → Account travels through Prayer, Home and Bible. Pages on a journey mount before it starts. Transition setup runs synchronously, and stable animated coordinates let a new selection continue from the current fractional position without stale endpoints from a previous transition. Settlement explicitly pins the page value and completed journey to the selected index. Measured page widths, vertical-only scroll restoration and non-scrollable web clipping prevent sideways drift. Resize and reduced-motion paths settle immediately. A duplicate visual icon/label row uses an inverse offset inside the pill's rounded clip, changing each covered fragment immediately as the pill passes. Its position and press scale match the normal row; the duplicate is hidden from accessibility.

The frosted navbar floats over the full-height background. Its shell uses an isolated stacking context; the foreground labels have a stable web compositing layer. The selected pill layers its orange pigment and sheen over the shell without a second moving backdrop blur. The header divider and decorative glass outlines are removed. On web, alpha masks fade page elements to zero opacity at the top (26 px) and bottom (140 px), with no black gradient painted over them. Native page content deliberately has no ancestor mask: UIKit visual-effect views cannot compose reliably beneath one. Bottom scroll clearance lets the final controls move fully above the player and nav.

`Glass.tsx` supplies frosted buttons, compact controls, reflection shortcuts, the reading-plan card and navigation material. Web controls use an 18 px backdrop blur with 128% saturation; the navigation shell uses 24 px and 145%. Native surfaces use Expo Blur with an explicit Android target. A continuous sheen, transmitted background lighting and soft shadows give the material depth without a decorative border. Orange glass keeps primary actions and the selected nav destination distinct; secondary controls retain theme text colors. Focus uses a soft glow. Native Android 31+ uses Dimezis blur; older Android versions retain the translucent material fallback and require device review.

CSS alpha masks create a backdrop root. Web therefore keeps a matching grain/light backdrop within that root for the cards to blur, plus an aligned full-height backdrop underneath that stays visible where content reaches zero alpha. Both move with the same page transform. Native uses the full-height background without that duplicate masked layer. Android buttons sample a separate background target, avoiding recursive sampling of their own blur layers.

The earlier velocity-based exposure and native viewport snapshots were removed after navigation regressions. Page movement uses the continuous track directly, with no motion-blur overlay or captured screen. True native lateral motion blur is **not implemented**. The liquid pill and frosted navigation shell remain. Native transition performance, material appearance and confirmation of the reported glass seam still need physical-device review.

Visited screens retain their scroll positions, drafts, passage selections, and plan views. Hidden screens are removed from accessibility traversal. Reduced-motion preferences skip the transition. The website's one-time expanding intro is not part of the requested tab-switch animation and is not ported.

## Highlights and comments

In either Bible view, signed-in readers choose **Highlight or add a note**, tap a first and last verse in one chapter, then **Add highlight or note**. One verse is also valid. Gold, orange and sage highlights are available, as well as note-only entries. Saving creates one private `annotations` document with its chapter ID, translation, range, short source excerpt, color, and comment. The Bible and Notes subscribe to that same document; the internal `comment` field supplies the user-facing note in both views.

Notes supports editing, changing color, confirmed deletion, opening the original verse range in Search, and searching loaded notes. Fifty recent notes load first, with **Load more** for older notes. Per-passage highlight listeners are separate, so older highlights still appear even when the Notes list has not paged back to them. Overlapping annotations are retained; the passage view presents the first matching highlight for a verse, while all saved comments remain available in Notes. Highlights are scoped to their selected translation.

Firestore rules constrain owner access, allowed fields, ranges, comment length, and timestamps, and preserve creation time on edits. A pending write shows **Syncing** in Notes; a server failure remains visible in the editor. Notes synchronization needs a connection; durable offline annotation drafts are not implemented. Authentication changes remount the private providers and retained screens, preventing another account from inheriting notes, journal drafts, pending completion UI, or notification intents.

See [backend setup and live-release requirements](HABIT_FEATURES_SETUP.md). Local browser checks do not verify APNs, FCM, native SMS app verification, or an App Store/Play Store build.

## Podcast player

`PodcastProvider` sits above the page and theme providers, so an episode keeps playing while readers navigate, change theme, or browse other plan days. The mini player shows the active episode, progress, and speed, with play/pause, close, and a return-to-episode shortcut. Selecting Play for another day switches the source. No episode auto-resumes after an app restart.

The audio streams from the official RedCircle RSS enclosure. `PlayerWaveform` from `react-native-waveforms` 0.1.3 displays 96 genuine build-time RMS values per episode, with live Expo Audio PCM updating heard bins and the current level during supported foreground playback. This keeps a real waveform visible while paused. The bundled reference data totals 66,394 bytes; audio is not bundled or uploaded. A 4.5-pitch bright trail is painted only through the bars. The white anchor averages four preceding displayed bars with an eased 180 ms height change. Both players and the rest of the app derive orange accents from `#F05A00`. The media clock controls progress at 1×, 1.25×, 1.5×, and 2×; pitch correction preserves the voice. Stable renderer components retain waveform nodes during playback, and UI-thread transitions ease touch feedback. [The request audit](REQUEST_AUDIT.md) records the neighboring-bar falloff and final verification.

Background audio is enabled in the Expo plugin/session, resolved iOS configuration includes `UIBackgroundModes: ["audio"]`, and the engine registers episode metadata and seek controls for the lock screen. However, actual Expo Go lock tests stopped playback with PCM sampling both enabled and disabled. The user explicitly deferred that unresolved issue; configuration and foreground browser playback do not establish working locked playback. Force quitting iOS also stops audio. Android live PCM is disabled to avoid Expo's microphone permission requirement; its complete reference waveform remains visible. [Podcast details](PODCASTS.md) document data, behavior, and remaining validation.

## Time settings and product copy

Reminder time and quiet hours use hour/minute/AM–PM pickers. Stored schedule values keep the existing 24-hour format, so notification policy and backend payloads are unchanged. The picker exposes its selected state and modal heading to assistive technology.

The copy pass used [The Bible Dept.](https://www.thebibledept.com/), its [Start Here page](https://www.thebibledept.com/start-here), and [ARMA](https://www.armacourses.com/) as references for accessible Bible teaching and clear next steps. Their course sales, urgency, and promised outcomes are not app feature claims. [Tom’s Guide’s five signs article](https://www.tomsguide.com/ai/how-to-spot-ai-writing-5-telltale-signs-to-look-for) supplied editing checks for generic filler, canned openings, press-release language, and uniform enthusiasm. Those are style criteria, not proof of AI authorship.

Product headings now name the task: **Today’s reading**, **Track your reading**, **Write a prayer**, **No notes yet**, and **Finished this chapter?** Notes, prayers, saved chapters, reading streaks, and local plan position use consistent names. Instructions and errors explain the next action, and local storage stays distinct from account synchronization. Scripture, episode titles, and the host's teaching were not rewritten.

Browser checks covered retained waveform nodes, playback across pages, seeking, the podcast anchor, rapid navigation and exact settled page positions at 390 and 704 px widths.
